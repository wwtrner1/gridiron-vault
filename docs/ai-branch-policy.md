# AI branch policy

This repository is deployed to Netlify. A recurring failure mode is when an AI coding session or automation branch pushes or builds against an older branch without going through the normal PR flow. Netlify then sees the same commit(s) already uploaded and reports:

> already uploaded by a previous deploy with the same commits

That message is a duplicate deploy signal, not proof that `main` is broken.

## Required workflow

1. Confirm the active branch before starting an agent run.
2. Never let an AI assistant work directly on `main`.
3. Create or use a feature branch for AI work.
4. Open a pull request and let preview builds validate the change.
5. Merge only after repository checks pass (`npx tsc -p .`, `npm run build`, `npm run test:server`, `npm run test:e2e` — the `Checks` workflow runs all of them on every PR).
6. Delete the temporary agent branch after merge.

## Branch naming rule

If the branch name looks generated by AI tooling or a sync service, treat it as disposable:

- `agent-*`
- `copilot-*`
- `claude/*`
- `netlify-*`
- `floot-*`
- `lovable-*`
- anything auto-created by a runner or sync mechanism

These branches must go through a pull request before they ever land on `main`.

## Production safety

The deployment path is:

`agent branch -> PR -> main -> Netlify production deploy`

Never:

`agent branch -> main directly`

This preserves the preview/build gate and prevents duplicate Netlify deploys from stale agent branches.

## Enforcement

### The `AI branch guard` workflow (`.github/workflows/agent-branch-guard.yml`)

Runs on every push to `main` and fails when the push came straight from an AI or automation account, or from a commit whose message names Copilot or an agent, **unless the commit belongs to a merged pull request** (a PR merge is the approved path, even when the branch was `agent-*`). It runs after the push lands, so it is an alarm, not a lock: a red run means something skipped the PR flow and should be reviewed. The lock is branch protection.

### GitHub branch protection for `main`

Settings → Branches → Add branch protection rule for `main`:

- Require a pull request before merging
- Require approvals: 1 is usually enough (see the note below for a solo maintainer)
- Require status checks to pass before merging. Required checks:
  - `Checks / typecheck-and-build`
  - `Checks / server-tests`
  - `Checks / browser-tests`
- Require branches to be up to date before merging
- Do not allow bypassing the above settings
- Optionally restrict who can push to `main`

This is the actual enforcement that prevents stale AI branches or duplicate Netlify deploys from reaching production.

> **Solo maintainer note:** GitHub never lets a PR author approve their own PR. With one maintainer, "Require approvals: 1" plus "Do not allow bypassing" means nothing can merge, and the Dependabot auto-merge workflow stops merging too. Until there is a second reviewer, set required approvals to 0 and keep the required status checks; that still forces every change through a PR and green checks.

### Netlify-side sanity check

- Verify the production site is configured to deploy from `main`
- Ensure preview deployments are enabled for PRs
- Confirm the branch list does not include auto-generated AI branches as production deploy targets
- Delete any stale agent branch that was previously used for the failed deploys

## What this fixes

- an old AI branch
- a duplicate same-commit deploy
- "already uploaded by a previous deploy with the same commits"
- a stale build that looks like `main` even though production is unaffected
